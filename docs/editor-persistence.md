## Consumer contract (Rust is authoritative)

`apps/server/src/features/editors/api.rs` owns schemas and operation metadata. Regenerate the public API/RPC/Query contract mechanically; do not copy these shapes into TypeScript. The public vanilla binding encapsulates necessary local byte transport and retained-output recovery:

```ts
const backend = sdkClient.editors.backend({
  id: file.id,
  // Optional, explicit user-selected destination; omission never implies the own root.
  destination: { parentId: null },
});
const document = await backend.open({ signal });
const bytes = await backend.download(document, { signal });
const result = await backend.save({
  sessionId: document.sessionId,
  expectedRevision: document.revision,
  saveId, // retain alongside exactly this captured output for ambiguous-response retries
  output: { name: document.name, bytes: editedBytes, intent: "replace" },
}, { signal });
// The existing createEditorSession({backend,messages,maxBytes}) owns frame attachment/recovery.
```

`editors.available({})` is a safe instance-capability query returning `{apps:[{app,version,inputExtensions}]}` (at most four). A single bounded DB read intersects current exact-version enablement with the verified configured catalogue and storage availability. It exposes no file or user metadata and grants no authority. The app/public-share provider may cache its generated Query result to show eligible entrypoints without per-row requests; `open` still checks current capability and file authorization if cached presentation becomes stale. Input extensions originate in the same Rust mapping used to select editors. The renderer must not maintain its own app/version/path registry.

The independently implementable HTTP/RPC protocol beneath that binding is:

```ts
const document = await sdk.rpc.editors.open({ id: file.id });
const download = await sdk.rpc.editors.download({
  sessionId: document.sessionId,
  expectedRevision: document.revision,
});
// Download application URL using the SDK's authenticated bounded binary transport.
// The vanilla editor binding owns local hashing and multipart byte transport, not domain policy.
const upload = await sdk.rpc.editors.prepareSave({
  sessionId: document.sessionId,
  saveId, // stable for this captured output, including retries after a lost response
  expectedRevision: document.revision,
  name: output.name,
  size: output.bytes.byteLength,
  sha256, // 64 lowercase hexadecimal SHA-256 digits over exactly these bytes
  intent: output.intent,
  saveMode: "manual", // optional; omitted is manual, "automatic" is replace-only
  // Required for save-as/export, forbidden for replace. null means an EXPLICIT own-root choice.
  ...(destination ? { destination: { parentId: destination.parentId } } : {}),
});
// Use the existing uploads.part + authenticated PUT protocol for missing numbered parts.
const result = await sdk.rpc.editors.completeSave({ sessionId: document.sessionId, saveId });
// result: {status:"saved", revision, file}; acknowledge only after this durable result.
```

`EditorDocument` has `sessionId`, `app`, `version`, required `assetUrl`, required `bridge` and `protocol`, `name`, `revision`, `writable`, `maxBytes`, nullable `replacementName`, and `outputFormats: [{extension,kind:"document"|"export",maxBytes?}]`. Rust generates `bridge: "upstream-host-parent" | "hyori-correlated-host-v1" | "hyori-correlated-host-v2"` and `protocol: null | 1 | 2` (numeric literals, not a broad number). The server emits only the consistent corresponding pairs from verified capability metadata. Native host features require the exact pair `bridge === "hyori-correlated-host-v2" && protocol === 2`; consumers must not infer them from a filename or app name. Current server producers include each output's byte ceiling; optionality permits older local protocol fixtures, with the application ceiling as fallback. Save IDs are 1–160 ASCII letters/digits/underscore/colon/hyphen (UUIDs and Deck's correlated `openId:sequence` are valid). Revision tokens are canonical nonnegative signed-64-bit decimal strings (`0`, `1`, …), not client counters or timestamps. The SDK must preserve the exact token. Download descriptors include `?revision=...`; each GET rechecks session, credential, current source revision, and bytes. Stale URLs fail, never becoming historical access or downloads of a newer revision under an old baseline.

The saved `revision` is the source's new revision for replacement, or its unchanged baseline for save-as/export. `file` identifies the actual saved destination. Replayed results preserve the committed outcome without rewinding session state. Capability flags are refreshed from current authority. Generated errors are ordinary `ApiError` codes; `resource.conflict` is a conflict, `access.denied` does not by itself establish a precise read-only reason, and transport/storage failures must remain ambiguous until the same save ID reconciles. There is no server assertion that a failed response proves no commit.

Removing runtime configuration denies old sessions even if their DB rows remain enabled. Apps absent from the verified catalogue remain unavailable without globally blocking other verified apps.

## Server decisions and bounds

- Open captures the authorized source revision and exact app/version. A session binds to the initiating active account, or the exact original anonymous grant digests, never all holders of the same link. It is not a bearer credential. Owner activity, current role, grant expiry/revocation and the asset enable/version gate are checked again on reads, prepare, ingest, acknowledgement, publication and terminal replay.
- Replacement requires current source Edit permission. Read-only Viewer sessions may Save As/export only with current source Read access and an explicit independently writable destination; they cannot replace the source, infer an own-root destination, or bypass the original revision check. Anonymous Viewer holders need an actual Contributor/Editor destination grant. Persisted intent drives the same policy on generic upload ingest/publication/replay. Directly shared Editor files can be replaced without permission to list their parent. Existing owner-only deletion/history policy is unchanged.
- Optimistic conflict rejection compares the original/session baseline during prepare and publication. Successful replacement advances only that session. Concurrent originally-opened sessions cannot silently overwrite one another. Rename/move/trash and ordinary replacement participate through server metadata revisions.
- Save-as/export require an explicit destination and independent destination upload authorization. They create a new file or fail on a name collision, never replace the source or add its history. PPTX opened in Deck has no replacement name: native conversion needs a new destination.
- Save ID, request fingerprint and upload linkage commit with the unique-key intent/reservation before S3 begin. Same ID/input returns the same upload and durable result across restart; changed input/hash is rejected. Multipart streams, immutable object accounting, previous versions, reservation release, leases and exact-key cleanup reuse Uploads. Direct generic uploads completion cannot bypass the editor policy/validation hooks.
- Final immutable output is SHA-256 verified and signature/container-gated outside retryable transactions before publication under the same upload fence. No document decompression or full parser runs on the API server. Original-download identification uses bounded 4 KiB header and 1 MiB tail range reads, not a second whole-original read. Output validation retains at most the same header/tail bounds while streaming the full digest, with a 120-second inspection deadline. ZIP directory admission is at most 4,096 entries and 256 MiB advertised expanded bytes; these bounds do not establish parser safety or fidelity. Uploaded input may remain unsupported/corrupt even when its name or MIME looks valid.
- The browser host ends its session when the frame is removed and on a non-persisted `pagehide`. It does not on `beforeunload`, which a person can cancel, or on a persisted `pagehide`, whose page may return from the back/forward cache with its work intact. A session that never gets to close, because a tab crashed or a cached page was evicted, is released by expiry.
- Sessions expire after 24 hours without sliding renewal. Session admission caps remain 32 per owner/principal and 256 per source owner; pending uploads remain capped at 128 per destination owner. Save metadata now has **two bounded buckets**, at most 128 pending/ambiguous mappings plus the latest 128 durable outcomes, with a hard **256 total mappings per session** (changed from the old 128 all-time total). Older completed outcomes that are not safely eligible for pruning remain protected within that total; admission fails conservatively when they fill it. Maintenance removes at most 256 saves and 256 eligible sessions in one transaction, aborting pending uploads to release reservations while retaining exact-key cleanup inventory. A single full session therefore fits one close/expiry batch. Purge includes source-owner and initiating-account records. Expired IDs cannot be recreated through prepare.

## Automatic saves, history and bounded reconciliation

`EditorPrepareSave.saveMode?: "manual" | "automatic"` is persisted and included in the stable-ID fingerprint. Omission remains absent in the serialized fingerprint so existing omitted-mode requests can replay unchanged; its behavior is manual. Explicit automatic mode is valid only for replacement, not Save As/export. This persistence capability does not require a protocol-2 renderer: independent clients and synthetic persistence fixtures may call it through the ordinary authorized API. Native frame request-save `reason` is a separate local protocol field, not a second backend policy owner.

Every save still writes a distinct immutable object with the full reservation, fresh authority, expected-revision fence and verified digest. Manual replacement always checkpoints the prior source. The first automatic replacement also checkpoints it. Within **60 seconds of that checkpoint** (not a sliding interval reset by every write), another automatic replacement may omit a new history row only for the exact current revision/key produced by this same session's previous automatic save. The recorded upload, initiating uploader and durable result must agree. Manual writes, another session, changed revision/provenance, restore or an elapsed window force a checkpoint or the normal stale-session conflict. Existing history, another current file, a pending replacement, an active session at that revision or queued/processing media work protects the prior key and forces a checkpoint. There is no history deletion or reduction in durable current-save frequency.

Publication atomically numbers durable outcomes and retains the latest 128. Pruning considers only older completed results whose original baseline **and** saved source revision are strictly below the session's now-current revision. Pending/ambiguous and current-baseline results are never pruned. Protected extra outcomes count toward the hard 256 total; no pending/session-cap raise, silent pending eviction or client session rotation compensates for unavailable safe reclamation.

### Retired save-ID fence

Exact retained mapping replay is checked **first**. Before admitting an unmapped ID, the server checks a per-session **128 KiB conservative Bloom fence**, version 1. SHA-256 hashes the UTF-8 bytes of `hyori-editor-retired-save-id-v1`, a zero byte, then the exact save ID. The first seven non-overlapping big-endian 32-bit words, modulo 1,048,576, select bits (least-significant bit first within each byte). Version, exact byte length and a SHA-256 checksum of the bitset are verified; corrupt state fails closed with `service.unavailable`. The bitset/checksum update and mapping deletions share the publication transaction, and retries never clear bits. Only pruning rewrites the blob; ordinary admission reads it, while ordinary session authorization projects fields without loading it.

A hit returns typed `resource.conflict`, including reuse with newly captured bytes or a mutated fresh revision after restart. Clients must not automatically choose another ID to hide this conflict. False positives can reject never-used IDs as the fence fills: this is a documented availability limitation, **not** a probabilistic data-integrity guarantee. The fence has no false negatives for retired IDs under the verified algorithm/transaction lifecycle. It is deleted with its session on close/expiry. Its bound is 128 KiB/session (up to 32 MiB for one owner's 256 sessions, before database overhead); it is never used for object GC or authorization.

### Exact-key collection and quota

Skipping a history row atomically marks the previous completed upload as superseded, preserving its durable result and unique-key tombstone and invalidating any earlier cleanup lease. Cleanup rechecks current/history/recovery references and active ownership before deleting that exact storage key. Quota remains charged until successful physical deletion and a matching fenced DB acknowledgement remove its `hyori_objects` inventory entry. Deletion followed by a crash/DB failure therefore conservatively retains quota until replay; an absent inventory row cannot be decremented twice. Deleting accounts are handled by account purge, whose cleared cleanup tokens fence stale acknowledgements. Tombstones continue periodic reconciliation for late storage effects after quota release and after session metadata disappears.

A successful publication sends a coalesced notification to the existing upload-maintenance owner, outside the DB transaction and without awaiting storage cleanup on the save response. The worker has a one-second fallback cadence, an eight-key priority pass for unreclaimed superseded objects plus an eight-key ordinary fair pass, and at most four storage reconciliations per pass. Slow/outage keys retain durable leases/retry times. This is bounded scheduling, not a measured throughput or open/save latency promise; deployment-specific saturation and storage-outage backlog remain operational limits.

## Explicit editor-session close

`editors.close({sessionId}) -> {success:true}` is an idempotent mutation. The original currently authenticated account can close its own handle without fresh file Read/Edit authorization; an anonymous holder must present an exact originally recorded **issued** grant credential. Revoked or expired-but-retained grant records can establish self-close identity without granting access to bytes. Unauthenticated, foreign-holder, missing and already-pruned IDs return the same success **no-op**, exposing no session metadata. Invalid/pruned identity credentials cannot claim ownership; normal expiry/account purge remains the fallback. Closing does not require storage availability or a still-enabled editor asset.

A successful self-close atomically removes that session and its bounded save metadata using the existing cleanup path. Its unfinished uploads are aborted, reservations released and publication leases fenced; exact-key upload tombstones remain for late or ambiguous S3 effects. Already published files and immutable history are preserved. Admission becomes available immediately after commit without raising the 32/256 caps, silently evicting other active/dirty sessions or retaining an unlimited collection of closed-session tombstones. No schema migration or global cleanup is introduced. Existing old-client abandoned handles remain until a valid self-close, their established expiry, or account purge.

**Close is not a save acknowledgement.** After closing, session download/new saves/terminal replay are unavailable. The SDK must not automatically close a currently attempted but unconfirmed save: keep its stable ID and bytes for reconciliation or the established TTL fallback. It may close clean/known-settled handles on disposal or late-open completion with bounded best-effort transport. A known durable late save may be acknowledged and then closed; local recovery bytes remain locally owned. Retried close is safe, but its generic success is not proof that a foreign or no-longer-authenticated handle was removed.

Focused close acceptance: three real disposable PostgreSQL/RustFS HTTP tests pass. They exercise 40 sequential open/close cycles followed by reopening, enforce the unchanged 32 genuinely active-handle cap, preserve unrelated handles under foreign/no-credential closure, and race close against open. Exact anonymous identity can release its handle after source revocation while a different holder of the same link cannot. Controlled storage barriers prove closing during late multipart begin or after object completion but before publication releases reservations and prevents publication/replay; retained exact-key cleanup removes the aborted object. A previously committed file and its version history survive closure. No existing LAN records were accessed or globally expired. Strict Rust, generated catalog 45, formatting and root anti-slop checks passed before this focused run; parent separately owns SDK/browser acceptance and release-image deployment.
