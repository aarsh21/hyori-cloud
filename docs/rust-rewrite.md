# Rust/PostgreSQL rewrite

Status: research and implementation in progress. This document records acceptance work, not a production-readiness claim.

## Authorized direction

See the 2026-11-05 rewrite decision in [product.md](product.md). Retain React/TanStack Start, the public SDK consumption model, RustFS, and all confirmed v1 capabilities. Replace the application backend and persistence with Rust/PostgreSQL and Better Auth Rust. Keep existing deployment data intact; no automated volume deletion or implicit database reset.

## Research

- NextFaster revision `cc38b9983aa2b80f71c8a50e6440cca83deebc6e`: reuse intent prefetch, deduplication, independent loading boundaries, and outcome-shaped operations. Its public two-hour catalog cache and image-prefetch endpoint are not appropriate for private, revocable files. A Next.js migration is not required.
- Better Auth Rust `1.0.0-alpha.5`, upstream revision `23c89f4e51999fe5767804879c82c60249cf9f84`, is MIT OR Apache-2.0 and uses Axum 0.8/SeaORM 2.0.0-rc.37. Pin the release: installation/security docs differ from inspected defaults. Use an owned adapter for atomic bootstrap/invites, digest-only session persistence, bounded KDF work, explicit rate limits and cookie/CSRF policy. Public mail recovery remains disabled under the unverified-email model. The dependency graph requires native ICU/OpenSSL; derive the ICU major from installed pkg-config metadata when building.
- Orbit revision `cf5ca05228a96d4fd99b5d058240de810c608911` (Apache-2.0): borrow thin handlers, owned persistence and durable job/reconciliation organization. It does not use Better Auth in the inspected identity implementation. Its global PostgreSQL advisory write lock and whole-file upload staging are not Hyori's chosen concurrency/resumability design.
- Omarchy: borrow principles only, with current `DESIGN.md` tokens, brand and Light/Dark/System unchanged. No verified site reuse license was found, and its branding reserves rights. Do not copy site code/assets. Screen splitting, precise focus, restrained chrome and responsive states fit Hyori; marketing layouts, music, shaders and theme-wipe animation do not.

## Preservation gates

- Protected atomic bootstrap; controlled accounts/invites; session invalidation and bounded password/rate-limit work.
- Admin aggregate usage and account purge without admin file-browsing access.
- Viewer/Contributor/Editor roles, owner-only deletion/moves/resharing, inherited and direct grants, shared uploads owned by the destination owner.
- Password/expiry/revocation on public links, including reauthorization of new binary requests, upload acknowledgement, and finalization.
- Cursor-paginated scoped listing/search/photos, stable errors, same-origin cookies and CSRF protection.
- Durable resumable multipart sessions; quota reservations; exactly-once metadata/accounting effects; replayable finalization and cleanup after process/storage failures. Failed replacement preserves old bytes.
- Trash groups, immutable versions, authorization of restore/history, account tombstones, and preservation of another owner's contributed files.
- One authoritative feature-local wire definition with mechanical client validators, types, operation metadata, Query consumption, and public SDK artifact tests.

## Performance characterization proposal

These are candidate benchmarks, not approved supported capacities or measured results. The existing host target is two CPU cores and 4 GiB for the complete stack. Record actual hardware, storage, versions, client, and network for every result.

Start with 100,000 items across ten accounts, folder sizes of 100/1,000/10,000, 20,000 media items, sharing, versions and trash. Exercise ten browsing clients alongside two uploads, a download and maintenance. Separate cold/warm caches and LAN/WAN conditions. A million-item dataset is stress characterization only.

Candidate gates: warm 100-item metadata page server p95 <=150 ms, search p95 <=300 ms, mixed-transfer metadata p95 <=250 ms, cached navigation p95 <=100 ms, and INP p75 <=200 ms. Bound page size, rendered rows, SQL/request count, speculative loading and per-transfer memory. Confirm target client devices and deployment conditions before publishing speed claims. Do not trade authorization or durability for a benchmark result.

## Current Rust slice and storage compatibility

The Rust service implements auth/bootstrap/invites and Files/Sharing metadata, and now wires `hyori-storage` into durable product uploads, quota reservations, replacement history, authorized streamed binary routes, and restart-safe upload maintenance alongside the existing auth cleanup. See the explicitly separated [Rust protocol and coverage](../packages/api/README.md#active-runtime-rust-behind-the-web-host). Personal Photos sources/timeline/albums, content-gated inline originals, admin users/quotas, durable account-owned-data purge and bounded isolated thumbnail/poster processing are now implemented. Worker deployment/UI adoption, complete inline-viewer/browser parity and complete editor integration remain open. The web host now mounts the private Rust service through the owned proxy; the previously verified immutable browser image does not verify newer source or worker changes.

Real RustFS `1.0.0-alpha.85` tests found that multipart prefix listing cannot enumerate an owner's keys correctly and may return one more upload than requested while omitting pagination markers. The adapter therefore exposes objects-only owner purge and bounded **exact-key, first-page** multipart cleanup, with no fictional multipart cursor or complete owner-multipart purge promise. Every product storage begin now has a committed PostgreSQL unique-key intent first, retained through completion/abort; durable tombstones repeatedly reconcile late or ambiguous storage work by exact key. Account purge now preserves this inventory instead of cascading it away. General unknown-key multipart enumeration is not established for the pinned RustFS release.

Before council: fallible contract construction and handler binding replace startup assertions/unwraps; initialization rejects duplicate/conflicting/missing/invalid schemas or bindings before database connection. Eight new failure-path tests, server strict locked Clippy, the actual compiled Rust evolution gate, byte-exact contract check, and the real SDK auth/folder/sharing/trash/restart path passed after that change. ## Administration / durable account purge — 2026-11-05

Existing Rust declarations now bind `admin.users`, `admin.setQuota` and `admin.deleteUser`; create-user/invite behavior remains unchanged. Public vanilla SDK and derived Query calls require no new catalog or frontend workflow. User pages are cursor-bounded at 100 and expose account identity plus aggregates only. Active-admin/session checks remain separate from ordinary file permission. Quotas accept nonnegative safe integers, may fall below current usage, and share the owner-row lock with upload reservation/publication checks. Deletion requires the exact current email and protects both admin-role accounts and the permanent bootstrap identity.

`0005_account_purge.sql` adds durable account/key associations, due ordering and five-minute fenced leases. Marking deletion atomically removes credentials and revokes active-account authority; narrow shared locks in existing Files session/owner policy close stale-transaction races without changing listing queries or grant-continuity logic. No global product lock or network/storage effect occurs inside retryable transactions. Maintenance independently claims at most two due accounts every five seconds, with at most 256 rows per metadata category, guarded leaf-first hierarchy removal and a 30-second network pass. Due time advances after partial/failing work; expired leases recover after restart. Auth/upload maintenance remain independent.

The worker preserves committed contributions owned by another account, clears the deleted uploader's attribution, and aborts incomplete contributions while releasing the correct destination owner's reservation exactly once. Original/history/trash objects, versions, distinct-object accounting, sessions/grants/shares/invites and personal Photos metadata are removed only within the target scope. Other people's album references to removed originals are pruned without deleting their surviving media. Parent/child and cascade guards avoid both the ordinary 1,000-descendant limit and unbounded FK cascades.

Owned completed/unfinished upload intents become redacted aborted tombstones; their publication and cleanup leases are fenced before storage work. Exact keys/multipart identity and account associations survive indefinitely. The worker reuses objects-only owner-prefix purge plus exact-key multipart reconciliation, never the known-broken RustFS multipart owner-prefix listing. Completion requires successful post-request key reconciliation, an observed empty objects page and empty scoped metadata. `deletedObjects` counts verified-absent **inventoried committed objects** exactly once, not transient multipart work or unknown orphan objects. Accounting resets only at completion. A nonregistrable `deleted:{id}` identity preserves safe FKs with no credential/name/email PII. Hourly account/key reconciliation continues after completion to catch arbitrarily late storage effects; complete is not a claim of eternal storage quiescence. Future derivative objects must use the owner namespace, and their metadata must join this cleanup before that feature ships.

## Durable derivatives / isolated media worker — 2026-11-05

Rust owns the optional timeline `derivative` field and new `media.get` safe read / `media.retry` mutation. `MediaDerivative` is a discriminated runtime-schema union: unavailable, queued, processing, ready, unsupported or failed. Only ready has a durable URL/dimensions; failed exposes a typed reason and `canRetry`. The optional timeline field decodes older verified server images unchanged. Original `previewUrl`, current preview revision identity, public grant continuity, file privacy and owner-only history semantics remain unchanged. Photos batches derivative metadata; there is no per-tile metadata waterfall or query-triggered processing.

`0006_derivatives.sql` supplies immutable-source/recipe jobs and independent exact-key artifact intents. Bounded maintenance backfill (32 sources) and one leased job per pass run off the upload/UI critical path. Five-minute job leases, three automatic attempts, six total attempts with explicit retries and persisted due ordering bound recovery. Every derivative S3 begin follows a committed unique intent, and publication rechecks lease, active owner and current original association. Restoring an immutable source reuses its canonical ready cache. Original quota accounting never charges cache artifacts.

The new `apps/media-worker` Rust executable accepts original streams only over a private Unix socket and launches fixed `/usr/bin/ffprobe` / `/usr/bin/ffmpeg` commands with cleared environment, explicit demuxer/protocol restrictions, no caller URLs/paths/arguments, capped pipes, deadlines and kill-on-drop. Startup verifies a nonroot, capability-free, seccomp/no-new-privileges, read-only, network-disabled Linux container with bounded cgroup v2 and private noexec/nosuid tmpfs. No DB/storage/auth credentials or Docker socket enter the worker. Backend FFmpeg execution and unsandboxed fallback do not exist.

Protective budgets were declared before implementation: 64 MiB source, 40 million pixels, 120-second video duration, 256-pixel output edges, 256 KiB normalized RGB PNG, one worker request, ≤1 CPU / 512 MiB / 64 PIDs / 96 MiB scratch. Original streaming stays bounded; only the small normalized result may be buffered in the backend. Output excludes EXIF/text/ICC chunks. First-frame posters, RGB/no alpha and stripped profiles are explicit limitations, not full fidelity or measured NAS capacity. Detailed production socket volume, environment, resource, license and retention guidance is in [the worker README](../apps/media-worker/README.md).

Account purge hooks remove job metadata, retain redacted exact-key artifact tombstones, wait for active worker leases, and include successful artifact reconciliation in completion. Other-owner contributions/cache survive. Objects-only owner-prefix sweeps plus exact-key multipart cleanup cover late ambiguous work without trusting the broken RustFS owner-prefix multipart listing. Ready cache is retained per immutable source/recipe until account purge; there is no global cache eviction/quota framework. Up to 256 KiB/artifact plus permanent intent metadata and transient multipart storage remains additional server overhead requiring operational sizing.

Functional evidence: four real media tests pass using PostgreSQL, pinned RustFS and an actual isolated worker. They exercise eight real synthetic formats, normalized output decoding, EXIF orientation, metadata stripping, malformed/mismatch/42-megapixel/121-second/oversized rejection, cancelled-input cleanup, unsafe-runtime refusal, lost S3 begin, lease expiry, outage/retry, replacement/restore, original quota, sharing/admin privacy/revocation, pending-worker deletion and late storage effects.
