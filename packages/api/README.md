# Hyori Cloud backend

## Active runtime: Rust behind the web host

The Rust service in `apps/server` currently implements protected authentication/bootstrap/invites, Files/Sharing metadata, durable product uploads, quota reservations and replacement history, authorized streamed binary downloads, personal Photos sources/timeline/albums, safe inline original-media GETs, isolated durable thumbnail/poster processing, admin user/quota management, and bounded auth/upload/media/account-purge maintenance. The vanilla public SDK consumes mechanically generated Rust feature contracts through `@hyori-cloud/api/client`; Effect is the generated client codec representation, not the Rust server implementation. `createBackendProxy({origin, backendUrl})` can mount that server behind the same-origin web host. The active web application mounts the private Rust service through the owned Node proxy; no legacy router or maintenance timer remains. See the [current application status](../../README.md) for packaged browser coverage of the media worker and opt-in editors. The historical acceptance notes below describe individual implementation stages.

### Public host and client boundaries

- `@hyori-cloud/api/rpc` exposes Rust-derived runtime schemas, operation metadata, `ApiRpc`, and inferred `Api`. Effect remains the client codec/runtime representation; there is no handwritten TypeScript operation catalog.
- `@hyori-cloud/api/client` exposes the same Rust-derived codecs and JSON operation metadata without constructing the Effect RPC transport graph. The browser SDK consumes this generated catalog; `/rpc` remains compatible for Effect RPC consumers.
- `@hyori-cloud/api` exposes the generic Fetch `createBackendProxy`, its configuration type and generated `Api` type. It imports no legacy core, DB, storage or Node runtime implementation.
- `@hyori-cloud/api/server` is the deliberate generic server-proxy entry. `@hyori-cloud/api/node` exposes `createNodeBackendProxy`, composing the **same** protocol/security proxy with Node HTTP(S) streaming transport. Node Fetch rewrites `Host`; the Node transport must preserve the configured public authority. It uses ordinary certificate validation, backpressure, body cancellation and no automatic retries.

```ts
import { createNodeBackendProxy } from "@hyori-cloud/api/node";

const proxy = createNodeBackendProxy({
  origin: "https://cloud.example.test",
  backendUrl: "http://private-rust-service:3002",
});
// Supply a Request whose URL uses the configured public origin.
// A TLS-terminating host must validate the actual incoming Host before mapping its private HTTP URL.
export const handle = (request: Request) => proxy(request);
```

`apps/web/src/server/api.ts` reads app configuration once and mounts `createWebBackendHandler`. Its runtime deployment inputs are `APP_ENV`, public `APP_ORIGIN`, **private** `HYORI_BACKEND_URL`, and the optional `HYORI_GATEWAY_CLIENT_ADDRESS_HEADER`. The backend URL and gateway header configuration are sensitive/dynamic in Varlock so they are not hydrated into HTML/client bundles. No setup token, auth secret, DB or S3 credential belongs on the web host. Production requires an exact HTTPS public origin; private HTTP behind the TLS gateway is allowed only with the preserved configured `Host`. Forwarding headers are never authority evidence. Origin/fetch-site checks remain enabled. Missing/unsafe configuration and backend connection failures return noncached 503 responses, never uninitialized success.

Client-address forwarding is **off by default**. To opt in, set `HYORI_GATEWAY_CLIENT_ADDRESS_HEADER=x-forwarded-for` (or one other HTTP header name which the directly connected gateway overwrites/appends). The host always strips caller-supplied `x-hyori-client-address`, `Forwarded`, `X-Forwarded-*` and `X-Real-IP`. With opt-in, it reads the configured source before stripping, selects the last comma-separated entry from a single physical field, and sends only a valid IPv4/IPv6 literal in `x-hyori-client-address`. Ports, IPv6 brackets/zone IDs, garbage, and duplicate physical fields produce no address. A runtime without Node raw-header evidence rejects comma lists rather than mistake duplicate fields for a gateway chain. Header names are case-insensitive; whitespace, a list of names, or the reserved outbound name are invalid configuration. The documented single Caddy `reverse_proxy` hop sets `X-Forwarded-For` from its client connection by default; the last-entry rule remains correct. With a CDN or additional upstream gateway, the last XFF entry can identify that proxy rather than the end user. Such a topology needs explicit upstream trust and a source header overwritten with the verified end-client literal at the directly connected gateway, not arbitrary caller-supplied evidence.

**The web host must be reachable only through the configured gateway when opted in.** A caller reaching it directly can supply its own source header and choose its rate-limit address. Checking the TCP peer only helps with an operator-supplied gateway allowlist or authenticated hop; private/loopback is not gateway identity. This option does not add either, and must not be used to expose the private web host or backend directly.

The adapter forwards only `/api/rpc` POST and `/api/storage/*` GET/PUT, preserves cookies/range/security headers, and streams byte bodies. It does not follow backend redirects, retry writes, reconstruct workflows or expose maintenance. Rust owns all domain authorization and lifecycle workers. The gateway must overwrite/preserve the real public Host, sanitize forwarded headers and keep the private web/backend network inaccessible to untrusted clients.

Functional acceptance: `bun run test:node-proxy` exercises actual Node HTTP transport, public Host, independent cookies, early upload streaming, cancellation and range bytes. `bun run test:rust-web-host <image>` starts unique disposable PostgreSQL/RustFS/Rust containers and the **built Nitro output**, with a locally generated TLS certificate trusted only by that test client. Public SDK setup/auth/folder/multipart upload/hash download, exact 206 length/416, Photos/safe originals, admin quota and misconfiguration/authority/CSRF checks traverse HTTPS → Nitro → Rust → PostgreSQL/RustFS. It checks that HTML/client assets contain no private backend URL. It is separate from full browser, worker, editor, capacity and deployment acceptance. The source/image/SDK results in the feature sections below describe their specific earlier slices; they do not imply verification of future worker code.

Login rate limits: a successful `auth.login` also sets `hyori_device` (HttpOnly, `SameSite=Strict`, `Path=/api/rpc`, 180 days), a random nonce with an HMAC binding it to that email under the auth secret. A browser presenting a valid device token for the email gets its own budget of 10 attempts per 15 minutes, so other people's failures can't lock it out. The optional gateway-derived `x-hyori-client-address` contract above lets Rust identify clients behind the host rather than treat its private TCP peer as every user's address. Without opt-in, the outgoing address evidence is unchanged: no forwarded address is sent. The backend owns the exact budgets and address eligibility; verify its deployed contract before relying on client-address limiting. New browsers can still be locked out of an email for a window; known ones can't.

Sign-in checks passwords in its own lane of 16 places. When every place is taken, `auth.login` answers `auth.signInBusy` (429) at once, without checking the password or counting an attempt, so retrying it is safe; the web sign-in retries it for about 3 seconds before showing that sign-in is busy. `auth.rateLimited` still means the attempt budget is spent: do not retry it automatically.

Each backend process holds at most `HYORI_DATABASE_MAX_CONNECTIONS` PostgreSQL connections (8 to 1024; default 48, a quarter of the 128 RPC slots plus the 16 upload operations). Keep the sum across replicas below PostgreSQL's `max_connections`.

### People and account sharing

- `users.search({query})` returns `{items: UserIdentity[]}`, where `UserIdentity` is only `{id,name,email}`. Any active signed-in account can search, but results never include the caller or inactive accounts. Search trims whitespace and accepts 1–100 characters. Case-insensitive matching is literal: use a name/email prefix for short or punctuation-heavy queries, or a substring when the query contains at least three consecutive letters or numbers. Responses have at most ten matches. The shared per-account budget is 240 searches per 15 minutes; hitting it returns `auth.rateLimited` (429). Admin account creation and deletion invalidate the SDK's `users` query scope.
- `shares.list({itemId})` returns `Share.recipient` alongside the existing `recipientId`. The recipient is null for public links or inactive accounts. `shares.update({id,role})` returns the updated `Share` and invalidates `shares`, `files`, `photos` and `media`. Only the item owner can change the role. Missing, revoked and public shares return `resource.notFound`; to change a public link role, revoke it and create another.
- Migration `0025_user_directory.sql` adds indexes and the PostgreSQL `pg_trgm` extension. Custom database deployments must have `pg_trgm` available; if the application database role cannot install trusted extensions, have the database administrator install it into the Hyori database before starting the upgraded backend.

### Password change and administrator recovery

The Rust API and generated SDK support `auth.changePassword({currentPassword,newPassword})`, `admin.createPasswordReset({userId})`, and `auth.resetPassword({token,newPassword})`. The account menu and Users screens consume them. Change returns `{success:true}`, replaces only the session account's credential, ends its other sessions, and cancels unused reset links. Its per-account budget is 10 attempts per 15 minutes, independent of sign-in and shared across the account's sessions; failed attempts survive rollback. New passwords follow account creation's 12–1024 Unicode-scalar policy and the existing bounded password hasher.

An active administrator receives `{token,expiresAt}` once, like an invite, to pass on privately; no email is sent and no password is exposed to the administrator. Tokens are 32 random bytes, stored only as SHA-256 digests, valid for 24 hours. One outstanding token per account is enforced in additive migration `0017_password_resets.sql`; issuing another replaces the previous token without ending sessions. Redeeming a current token atomically consumes it, changes the credential and ends **all** sessions of that account. Invalid, consumed, superseded, expired and deleted-account tokens all return `access.denied`. Reset returns `{success:true,userId}`; it does not sign the person in.

SDK mutations have automatic retries disabled. Change/reset clear old mutation records and non-auth query data and invalidate `auth.status`; reset immediately clears the affected cached identity before a fallible refresh, without clearing another account's identity. Feature hooks in `packages/features/src/auth/react/use-password.ts` consume these generated mutations without reconstructing server workflows. The interface worker must build the reset URL, show the returned token only while its dialog is open, and discard/reset dialog state on close. Individual session listing/revocation and recovery when the sole administrator forgets their password remain unsupported.

Interface handoff (operation-specific copy must override the existing generic email/password and access-denied messages):

| Operation                   | Input → output                                     | Expected failures and recommended feedback                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.changePassword`       | `{currentPassword,newPassword}` → `{success:true}` | `auth.invalidCredentials` (401): “Your current password wasn’t accepted. Try again.” This can also mean a concurrent password change won. `auth.required` (401): session ended, sign in again. `auth.rateLimited` (429): wait up to 15 minutes; do not retry automatically. `input.invalid` (400): new password must be 12–1024 characters; current password is required and at most 1024. Success: password changed; other sessions ended; this session continues. |
| `admin.createPasswordReset` | `{userId}` → `{token,expiresAt}`                   | `auth.required` (401): sign in again. `access.denied` (403): administrator access is required or the target account is no longer active; refresh Users. `input.invalid` (400): invalid account ID. Success: copy and privately share the one-time link before closing; expires at the returned instant. Creation itself ends no sessions.                                                                                                                           |
| `auth.resetPassword`        | `{token,newPassword}` → `{success:true,userId}`    | `access.denied` (403): “This link is invalid, expired, or already used. Ask your administrator for a new one.” Do not distinguish deleted accounts or replaced tokens. `auth.rateLimited` (429): wait up to 15 minutes; do not retry automatically. `input.invalid` (400): new password must be 12–1024 characters or the link is malformed. Success: all sessions ended; sign in with the new password.                                                            |

All three can return `service.unavailable` (503): keep the form recoverable and offer explicit retry. SDK validation failures (`SDK_VALIDATION`) should show field guidance; network/protocol failures (`SDK_TRANSPORT`, `SDK_PROTOCOL`) must not claim the password stayed unchanged, because a response can be lost after commit. Offer sign-in with the new password or a new administrator link when the result is uncertain. A lost create-link response can be recovered by explicitly creating another link, which invalidates the unknown one. There is no automatic replay or email-based fallback. Reset limits follow the existing secret policy: 10 attempts per token/client per 15 minutes and a 100-attempt ceiling across identified clients; without a trusted client address the token shares one 10-attempt budget.

### Notes and collaboration protocol

Rust `features/notes/api.rs` and `features/collaboration/api.rs` own the generated contracts. `notes.*` owns metadata, favorites, paginated owner history/checkpoints and restore. `collaboration.open/sync/close` owns principal-bound document sessions, current permissions, server-stamped presence and explicit durable receipts. `@hyori-cloud/client-sdk/collaboration` exposes the vanilla Yjs session; `@hyori-cloud/client-sdk/browser` supplies the optional authenticated IndexedDB recovery adapter. No editable content is mirrored into Query or global React state.

Migration `0024_notes_collaboration.sql` adds state, sessions, favorites and checkpoint tables without deleting existing data. Disposable test databases migrated with the unpublished Notes `0023` must be recreated; that number now belongs to the integrated thumbnails migration. A note is an ordinary authorized file item with reserved MIME `application/vnd.hyori.note`, a Notes parent hierarchy and no object key. Generic uploads cannot spoof that MIME or replace its collaborative head. Both Notes and Files renames require the observed title for Notes, so Files cannot bypass title conflict detection. Moves, Trash/restore, permanent deletion and account purge include nested notes and release collaboration quota charges. Live state and retained checkpoints count against the existing owner's quota; history pages contain 30 entries and no automatic pruning occurs.

Each sync reauthorizes under the existing serializable Files transaction and validates an isolated Yrs candidate on a blocking worker. Same-document exchanges queue before their database snapshots using a bounded process-local striped lock; PostgreSQL remains the cross-process correctness boundary. Content writes lock the document row; an unchanged poll neither locks that row nor writes presence until its three-second heartbeat is due. Changed selections still publish immediately. A closing, reloading or navigating page closes its session at `pagehide` with a keepalive request, so peers drop it at once; a tab that vanishes without saying so leaves peer lists after eight seconds without a heartbeat. Web Notes draws remote carets in an overlay outside the editable DOM and holds peers' content back while a local IME composition is open. Dependency-incomplete updates, extra roots, unsupported XML tags/attributes/marks, unsafe links, invalid relative cursors and excessive state/depth/node counts are rejected without changing the head. A committed receipt echoes exactly the captured batch; the SDK clears only that batch, not newer edits. Viewer/Contributor writes are denied. Restore preserves the replaced head, advances generation and fences stale sessions. Current shared-link password, expiry/revocation and active-account checks remain authoritative at every exchange. The 16-session cap is unchanged; a rejected open explains that the note is full and offers retry without discarding device recovery.

Unsigned public-link sessions share a twelve-lease sub-cap per note, across all public links and roles, inside the unchanged sixteen-lease limit. Classification uses the transaction's resolved actor: an active signed-in account remains signed in even with public-link credentials; valid legacy grants and stateless capabilities without an active account, including an expired account cookie, count as guests. No eviction or schema change is introduced. Both caps return the existing `auth.rateLimited` refusal and note-full interface.

`files.download` captures a committed Notes cut and returns a generation/sequence/revision-fenced `/api/storage/notes/{id}?fence=...` attachment containing lossless `.hyori-note.json` state. A changed cut fails rather than silently serving stale content. Native exports use the shared download admission and bounded body relay, including its idle deadline; the handler does not release admission ahead of the body. Editor Markdown/blocks exports are explicitly local snapshots; Markdown is lossy. No Office materializer or Notes→WordCraft conversion is implied. Bounds and remaining Notes limitations are in the root README; this transport is HTTP polling, not WebSocket broadcast, and no capacity guarantee is claimed.

### Rust upload/download protocol

The existing consumption is unchanged:

```ts
const task = client.uploads.start({ parentId, file, replaceId });
task.pause();
await task.result.catch(() => undefined);
const checkpoint = task.getSnapshot().checkpoint;
if (!checkpoint) throw new Error("No server checkpoint was obtained");
// After restart/reselection; checkpoint contains metadata, not local file bytes:
const resumed = client.uploads.resume({ checkpoint, file, confirmSameFile: true });
const committed = await resumed.result;
const { stream } = await client.downloads.open({ id: committed.id });
// Failed tasks expose retry(); cancellation is confirmed through cancel().
```

- `uploads.begin` commits a unique `owners/{owner}/{upload}` intent and the **full future size** reservation under the owner's PostgreSQL row lock before S3 begin. New shared files belong to the destination owner; authenticated uploader identity or anonymous attribution is separate. Begin is not automatically replayable. A lost begin remains inventoried and is cancelled when its first cleanup becomes due after ten minutes. A new owner's own upload expires 24 hours after begin or its last acknowledged part; uploads begun before migration 18 keep their original seven-day expiry. At most 128 nonterminal reservations per owner are admitted, including zero-byte sessions. A **contribution** (initiator other than the destination owner: another account, or the visitors of one public link, keyed by its share IDs) must receive a part within an hour of begin and of each previous part, capped at seven days after begin; cleanup then aborts it and releases its reservation. One initiator may hold at most 16 pending uploads in another owner's space, and at most half of the space still available to it (the owner's free bytes plus what it already holds); excess begins fail with `storage.quotaExceeded`. Migration `0012` adds the initiator column and its index. `uploads.incoming` (safe query) lists up to 128 pending contributions into the signed-in owner's space (ID, name, size, expiry, anonymous flag; never the contributor's identity), and `uploads.abort` accepts the destination owner as well as the initiator.
- Uploads are bound to the initiating active account, or to the original anonymous grant credentials (stored only as digests). Knowing an ID or holding another grant to the same link does not allow takeover. Every ingest, acknowledgement, and publication re-resolves current authority and destination/replacement revision. Moving/trashing a destination, revoking a grant, or disabling an account can invalidate work. An authenticated initiator may cancel their intent even after a destination/revision conflict; this cannot publish content.
- `uploads.part` is a safe read returning `PUT /api/storage/uploads/{id}/{number}`. PUT requires the same origin/host and cookies, an exact `Content-Length`, 8 MiB parts (last part exact), at most 10,000 parts, and one zero-byte part for an empty file. The `hyori-storage` adapter length-verifies backpressured streams, without whole-file/whole-part collection. Success is `{"ok":true,"value":{"partNumber":n,"size":bytes}}`: an acknowledgement of that part only, not the whole recorded part list (which can reach 10,000 entries); `uploads.status` remains the checkpoint read. A request body that delivers no bytes for 30 seconds fails the part and releases its lease. Repeating a **durably acknowledged** part drains/validates its size but does not rewrite storage; a missing acknowledgement can be retried. An acknowledgement requires persisted ETag plus exact size.
- Uploads and downloads are admitted separately, so neither can exhaust the other. A process admits at most sixteen upload begin/part/complete operations; one durable three-minute session lease serializes part writes/finalization across processes. The local PUT deadline is 125 seconds; the adapter bounds each S3 request to 120 seconds. A part PUT that finds another request's lease still held (for example its own earlier attempt whose connection died) receives `service.unavailable` (503, retryable), not `resource.conflict`; abrupt process loss can still require waiting for lease expiry. A concurrent completion may receive `resource.conflict`, not a fabricated completion.
- Download-like bodies (originals, previews, thumbnails, editor downloads and native Notes exports) are admitted up to 64 per process and eight per principal: a session, a public grant set, or (without credentials) the TCP peer address. Up to 56 more of a principal's requests wait up to 10 seconds for a slot (a thumbnail burst queues rather than fails); beyond that, or when the process limit is reached, requests receive 503 before any database or storage work. Hyper only polls a body while the client reads, so a spawned producer owns each stream and both admissions, feeding a two-chunk channel. When storage or the reader is idle for 30 seconds, or the body passes 900 seconds, the producer stops and releases its admission even though the stalled connection stays open; the response then fails rather than ending as if complete. Storage-backed ranges and headers are unchanged. The constants live in `apps/server/src/config.rs`.
- Completion validates every numbered part and freezes writes, then completes and HEAD-verifies the unique immutable object outside database retries. Ambiguous complete/HEAD failures leave a replayable finalizing intent. A fenced, freshly authorized PostgreSQL transaction commits file metadata, old-version history, one distinct-object quota charge, reservation release, and terminal result together. Abort clears the fence before reconciliation, so a late worker cannot publish. Stored terminal results are replayed only after current file authorization, with refreshed capability flags. Restoring a retained version does not charge the same object again.
- `files.download` describes `/api/storage/files/{id}?version=...`; each GET freshly authorizes and resolves the immutable key before streaming. Historical reads are owner-only. Single ranges support 200/206/416 with exact lengths; multiple/malformed/unsatisfiable ranges fail rather than becoming full downloads. Binary content is served as `application/octet-stream` with safe UTF-8 attachment encoding, `no-store`, `nosniff`, and sandbox CSP, including uploaded HTML/SVG. This route remains an attachment; inline originals use the separate preview route below. An already authorized download may finish after revocation; new requests must reauthorize.
- Runtime-owned maintenance claims at most eight due exact keys with durable five-minute cleanup leases and `SKIP LOCKED`. Each key's network pass is capped at twenty seconds; failures/pending pages retry after a minute. Clean terminal markers back off exponentially: an hour after the first clean check, doubling to a 30-day ceiling, so each costs about twenty visits a year instead of 8,760. A superseded object still referenced elsewhere waits from a minute up to a day. Each pass claims urgent work first (stale `starting` intents, expired reservations, unverified deletes, superseded objects) and fills the rest of its batch with revisits, using one partial index per class; a tick keeps claiming full batches, at most four. Due ordering persists across restart and advances failed keys behind older backlog. Inventory is retained indefinitely for late/ambiguous work; committed originals are never deleted by completed-upload cleanup. Pinned RustFS `1.0.0-alpha.85` cannot reliably enumerate owner multipart prefixes/pagination, so cleanup repeatedly uses bounded exact-key first pages, never an invented continuation cursor. Auth cleanup remains independent, and both workers stop before DB shutdown.

Configure all five `HYORI_STORAGE_{ENDPOINT,REGION,BUCKET,ACCESS_KEY,SECRET_KEY}` values explicitly (see `apps/server/.env.example`); there is no ambient AWS credential chain. Omitting all selects metadata-only fixture mode: upload/binary operations return `service.unavailable`, not storage success. A metadata download descriptor alone is not proof of stored bytes. Startup ensures the configured private bucket exists and fails closed on storage initialization errors. Existing migration checksums are preserved; the new upload migration does not delete deployment data.

### Rust Photos and safe original media

`photos.library` is the automatic library: it includes current, supported media the account owns, wherever it was filed. Uploads into someone else's folder belong to that folder owner. Incoming shares and saved source settings do not feed this timeline. Migration `0025_automatic_photos.sql` adds an owner/date index and nullable metadata fields with no original copies or item rewrite. The index builds take a write lock on `hyori_items`; plan an upgrade window for large databases. The legacy source and album APIs remain unchanged.

```ts
const folder = await sdk.rpc.files.createFolder({ parentId: null, name: "Pictures" });
const media = await sdk.uploads.start({ parentId: folder.id, file }).result;
const page = await sdk.rpc.photos.library({});
const next = page.nextCursor ? await sdk.rpc.photos.library({ cursor: page.nextCursor }) : null;
const details = await sdk.rpc.photos.details({ id: media.id }); // viewer only
const album = await sdk.rpc.photos.createAlbum({ name: "Favorites" });
await sdk.rpc.photos.addToAlbum({ albumId: album.id, fileIds: [media.id] });
const current = await sdk.rpc.files.get({ id: media.id });
const original = await sdk.rpc.files.preview({ id: current.id });
// query.files.get.getOptions({id}) and query.files.preview.getOptions({id}) derive automatically.
// Items carry thumbnail/poster state and previewUrl for explicit original viewing.
```

- `query.photos.library` and `rpc.photos.library` seek from an opaque cursor, at most 100 items at a time. Each item contains `timelineDate` (a `YYYY-MM-DD` calendar date) and `dateSource` (`capture` or `upload`). Sort is recorded local time or fallback UTC upload time, then ID, descending. Group by the date string, keep server order, and key by file ID: background indexing can move an item on refresh. There are no counts, folder walks, storage reads, or per-item metadata RPCs in a page request.
- `photos.details({id})` returns nullable `capture` (`localDateTime` and `offsetMinutes`, also nullable when the tag doesn't specify an offset) and nullable `location` (decimal `latitude` and `longitude`). Only the current file owner can read these fields; incoming shares and admin status do not grant access. GPS is never projected into a timeline, derivative image, or log. The underlying original may still contain GPS.
- Committed JPEG, PNG, WebP, GIF, AVIF, MP4, WebM and QuickTime files can appear before parsing. Binary reads still validate the declared type. Extraction handles EXIF capture tags on supported image containers and the worker's allowlisted video container tags; embedded data beyond the probe's limits may be absent. Replacements clear metadata in the same transaction, and restored originals can be inspected again. Backfill uses the existing worker admission and prioritizes thumbnail jobs; already ready derivatives are not regenerated. A disabled or old worker leaves date fallbacks until a capable worker is available.
- Legacy `photos.sources`, `setSources` and `photos.timeline({albumId?})` remain available. Source selection is configuration, never grant authority. A legacy timeline is ordered by upload timestamp then ID, returns at most 100 items, and authorizes selected sources and album members independently. Explicit **All my files** in the legacy API is owned-only. Shared sources require current authorization to both the source and media.
- Albums are personal reference collections, independent of source selection, limited to 100 per account and 1,000 references per album. An add request contains at most 100 IDs and deduplicates membership. Serializable transactions enforce capacities atomically. Album `count` is **stored references**, including references subsequently trashed/revoked; timeline media is current-authorization filtered, so visible count may be smaller. Unknown/other-account albums and invalid, nonmedia or unauthorized members fail generically with `resource.notFound`, without partial additions. Originals are never duplicated. Album rename/delete/removal and sharing are not operations in this slice.
- `files.get({id})` is a current, authorized, nontrashed `FileEntry` read, including public-link holders. It is not owner-only history and does not rely on an upload-tray snapshot. Admin status grants no file access.
- `files.preview({id,versionId?})` is a safe metadata query returning `Download` with an application URL `/api/storage/previews/{id}?version=...`, not a storage URL. Unsupported declared types return `input.invalid`. The descriptor is not proof of decodability; GET performs validation. Historical preview metadata and bytes remain owner-only.
- Every preview GET resolves current session/share/expiry/revocation and a current immutable `ContentDescriptor`. A matching `If-None-Match` returns 304 after authorization and before any storage read. Otherwise it inspects **at most 4 KiB** from that exact object under a 30-second header-read deadline. A bounded signature/container-header gate identifies an explicit image/video family and requires an exact declared-MIME match. SVG, HTML, XML, PDF, unknown/truncated signatures and mismatches fail with `input.invalid`; no fallback image or active uploaded document is served inline. ISO-BMFF files require an initial bounded `ftyp` with recognized AVIF/MP4/QuickTime branding; WebM requires a structural EBML `webm` DocType. Some otherwise decodable variants outside these rules are intentionally rejected.
- Validated original bytes use the same storage stream, single-range parser, exact-length checks, process transfer admission and 30-second idle/900-second streaming deadline as attachments. The semaphore spans header inspection and response-body lifetime. Preview responses carry exact 200/206/416 lengths, `private, no-cache` plus an opaque immutable-object ETag on 200/206/304, `nosniff`, sandbox CSP and encoded inline disposition. The web proxy preserves this policy only for successful previews and derivatives. Browsers may store bytes but must revalidate before reusing them; no freshness interval authorizes reuse without a server round trip. No whole-file buffering or user-media background job runs on a query/refetch. Each subsequent GET repeats authorization; matching immutable bytes need no repeat signature inspection. Revocation cannot retract already-opened bytes. Standard original and editor downloads remain `no-store` `application/octet-stream` attachments.

**Originals are not thumbnails or video posters.** This header safety gate is not full decoding, antivirus scanning, codec/fidelity assurance or a browser acceptance test. A consumer using original URLs for tiles still transfers originals. The separate durable derivative protocol below now supplies bounded thumbnails/posters and explicit states; UI adoption and real-browser fidelity validation remain separate work. No user media was sent to an external service; the eight test fixtures are locally synthesized red squares with [CC0 provenance](../../apps/server/tests/fixtures/media/README.md).

### Rust administration and account-owned-data purge

The existing public contracts are now bound to Rust; no new client method catalog or frontend deletion workflow is needed:

```ts
const users = await sdk.rpc.admin.users({ cursor });
await sdk.rpc.admin.setQuota({ userId, quotaBytes });
const purge = await sdk.rpc.admin.deleteUser({ userId, confirmEmail });
// purge: { userId, state: "pending" | "complete", deletedObjects }
// query.admin.users.getOptions({cursor}) and the existing derived mutation options are unchanged.
```

- Every admin operation requires a current session for an active admin. `users` returns at most 100 accounts plus a cursor, with account identity, role/status and aggregate used/reserved/quota bytes only. It never lists file names, paths, object keys or previews. Deleted tombstones are omitted. Ordinary Files/Photos/Sharing authorization never treats the admin flag as browsing permission.
- `setQuota` locks the current target account and rejects nonactive targets. Nonnegative safe-integer quotas may be lowered below current usage/reservations without deleting bytes; subsequent upload begin/publication must pass the existing quota checks. Protected bootstrap identity and all admin-role accounts cannot be deleted; no account promotion or bootstrap reset occurs.
- `deleteUser` requires the **exact current email**, atomically marks the account `deleting`, deletes its credential and creates a durable purge record. Account-status checks immediately invalidate session identity, owned-file access and grants issued by that account. Narrow shared locks on active session/owner authorization fence previously started metadata transactions against the deleting-status update. Public anonymous grants issued by unrelated active owners remain separate bearer capabilities; account deletion does not revoke another owner's public links.
- The mutation commits the deletion, wakes account maintenance and returns aggregate progress, normally `pending`. It never runs the purge itself, so a slow storage purge can't turn a committed deletion into a 503 at the RPC deadline. Completion is owned by server maintenance, not repeated SDK/UI delete commands. `users` remains a safe query: it can display `deleting` until the completed account disappears. Reissuing deletion after the synthetic deleted tombstone is installed returns `resource.notFound`; clients should not use the mutation as a polling endpoint.
- `0005_account_purge.sql` adds durable account/key associations, five-minute fenced leases and due-order indexes. Runtime maintenance checks every five seconds, claims at most two due accounts with `SKIP LOCKED`, and advances successful incomplete work by one second or failed work by one minute. Each metadata category processes at most 256 rows per account pass; child/versions/share/album-reference guards make item removal leaf-first without unbounded cascades or the ordinary 1,000-descendant mutation limit. Storage work is outside retryable transactions, with a 30-second account-pass network deadline and the existing per-key 20-second cleanup deadline. Shutdown/cancellation leaves durable leases recoverable after expiry. These are scheduling bounds, not completion-time guarantees under backlog.
- All originals, trash, immutable versions and distinct-object inventory owned by the target are reclaimed. Sessions, credentials, issued/recipient shares, grants, issued/addressed invites, personal Photos sources/albums and obsolete album references are pruned in bounded batches. Other accounts' committed contributions survive; their `uploaded_by` attribution is cleared when it refers to the deleted account. The target's pending uploads into another owner's folder are aborted and release that **destination owner's** reservation exactly once; committed uploads into that folder are never converted to deletion markers.
- Owned terminal and unfinished uploads become redacted, fenced `aborted` records: name, result, MIME, parent, uploader, grant digests and replacement metadata are cleared while exact key/multipart identity remains. Upload part metadata is also pruned. The existing cleanup adapter drains known multipart IDs and exact-key first pages and removes aborted objects. A stale completed-state cleanup cannot certify a newly aborted key because its cleanup token is invalidated. A late publisher cannot regain a cleared publication lease or active account authority.
- Completion requires no remaining scoped metadata, successful post-request reconciliation of every associated upload key, and an observed **empty objects-only owner-prefix page**. Merely deleting a nonempty last page does not certify emptiness. Missing storage configuration remains pending even when metadata is empty. Verified-absent committed object inventory is reclaimed in bounded batches; `deletedObjects` counts those distinct inventoried objects cumulatively and exactly once, not transient multipart uploads, repeat tombstone deletions or uninventoried orphan objects. Used/reserved/quota values reset only when the account completes.
- The retained identity is `deleted:{opaqueId}` with name `Deleted account`, no credential and zero accounting; its email is not registrable by the normal email parser. Permanent bootstrap state is untouched. Minimal account/key tombstones remain indefinitely and are revisited hourly, including after completion, to catch late ambiguous S3 begin/parts/complete work. **Complete means the committed inventory and currently observable storage were reconciled, not a promise that arbitrarily delayed storage work can never appear later.** RustFS alpha.85's broken owner-prefix multipart enumeration is never used as proof of cleanup. The objects-only prefix sweep also removes unreferenced objects in that owner's namespace; the derivative job/artifact tables below now participate in that bounded cleanup, while any future storage-backed feature must register its own metadata/inventory hooks.

Functional evidence: `apps/server/tests/admin.rs` adds three passing real PostgreSQL tests (two with pinned RustFS), covering admin/session isolation, pagination, quota/publication denial, exact confirmation/protected bootstrap, metadata-only pending, a 1,200-item hierarchy, 300 grant rows, originals/versions/trash/Photos/invites, actual partial object deletion followed by outage/retry, restart, lease expiry, concurrent delete/worker claims, correct reservation accounting, contribution preservation, late begin after completion and in-flight completion fencing. ### Durable derived thumbnails and video posters

`0006_derivatives.sql` and `apps/server/src/features/media` own the job, exact-key artifact inventory, authorization and public schemas. The private decoder is a separate `apps/media-worker` executable/container. See its [deployment, protocol, budgets and license notes](../../apps/media-worker/README.md); the backend never launches FFmpeg.

```ts
const page = await sdk.rpc.photos.timeline({});
for (const item of page.items) {
  const derivative = item.derivative; // optional: older backend images remain decodable
  if (derivative?.status === "ready") {
    // A normalized PNG thumbnail or video poster; not the full-screen original/video source.
    console.log(derivative.kind, derivative.url, derivative.width, derivative.height);
  }
  // item.previewUrl remains the safe ORIGINAL, including video playback.
}
const state = await sdk.rpc.media.get({ id }); // safe read, no job initiation
if (state.status === "failed" && state.canRetry) await sdk.rpc.media.retry({ id });
// query.media.get.getOptions({id}) and mutation.media.retry derive from Rust declarations.
```

The Rust-derived discriminated union is `unavailable | queued | processing | ready | unsupported | failed`. All variants carry thumbnail/poster kind and current `sourceRevision`. Ready alone carries a nonnullable URL and dimensions; unsupported/failed carry a typed reason, and failed exposes `canRetry`. Pending/failure states cannot fabricate a ready URL. The optional timeline field preserves decoding of the verified pre-worker backend image. Queries do not enqueue, mutate or trigger decoding; one batch metadata lookup supplies timeline derivative states without per-tile RPCs.

Upload publication enqueues the new file's job in its own transaction. Maintenance also sweeps 256 items per five-second pass in primary-key order, resuming where it stopped, for sources that gained bytes another way (restores, copies, pre-existing files). It keeps claiming due jobs while they remain, up to 64 per tick and within the tick interval (previously one per tick, 720 an hour), with five-minute leases, three automatic attempts and at most six decoder verdicts including explicit retries. A Retry attempt that fails on a storage or worker outage, or loses its lease, is requeued with capped 20–640 second backoff instead of spent. Upload commit/original download never waits for the decoder. A canonical immutable-source + recipe record allows restore to reuse a ready artifact; the URL also carries the current revision identity. Every derived GET freshly authorizes the current original and verifies the selected artifact belongs to its current immutable source. It then returns 304 for a matching opaque ETag without reading storage, or streams known normalized PNG with `private, no-cache`, ETag, nosniff, sandbox and the shared range policy. Replaced-source or revoked/private artifact URLs fail rather than exposing old cache bytes. Original history remains owner-only.

Processing uses an operator-configured private Unix socket, not a caller URL. The worker refuses startup without Linux nonroot/zero-capability/no-new-privileges/seccomp, read-only root, no network, cgroup CPU/memory/PID limits and bounded private scratch. It has no PostgreSQL/S3/auth credentials and rejects unexpected environment names. The backend streams at most 64 MiB input; the worker uses scratch and capped subprocess pipes. Fixed allowlisted demuxers/protocols and explicit disabled external MOV references are used. Protective limits: 40 million source pixels, 120-second video duration, 256-pixel output edges, 256 KiB RGB PNG, one processing request, 60-second request deadline, 10-second probe and 20-second encode. Actual decode/normalized-output tests pass for all eight existing synthetic formats, including one verified EXIF orientation case. These are protective bounds and exercised examples—not NAS throughput, comprehensive format/alpha/HDR/color fidelity or browser measurements.

Every derivative S3 begin has a committed unique object-key intent first. Storage/decoder calls are outside retryable transactions; publication rechecks owner activity, job lease and current source association. Failed/ambiguous keys retain exact-key cleanup records indefinitely. Cache artifacts live separately under the owner's derivative namespace and do **not** consume original used/reserved quota. Implementation default: retain a ready cache per immutable source/recipe until permanent deletion releases that source's last item or version reference, or account purge, without a global eviction/cache-quota framework. The releasing transaction retires the source's jobs and fences its ready artifact for exact-key removal; a live worker lease keeps the original until it lapses, then the claim retires the job. Each claim locks at most 32 due jobs before classifying them; those it can't run (source only in Trash, inactive owner) wait an hour, and restoring an item from Trash makes those deferred jobs due again without shortening a failure back-off. Every expired worker lease is settled, whatever its attempt count and even when the decoder is disabled (migration `0015`), so a crashed worker never keeps a deleted original; budget up to 256 KiB per ready artifact plus permanent intent metadata and transient multipart work. Retention/capacity sizing remains open.

Account purge now prunes media jobs, waits for active worker leases to settle/expire, fences and redacts artifact intents, and requires their successful post-request exact-key reconciliation. Owner-prefix object sweeps and exact-key multipart tombstones continue to catch late begin/complete effects; the broken RustFS multipart owner-prefix enumeration is not used. Other-owner contributions and their cache artifacts survive. An already-open stream cannot be recalled, and completion does not imply all future delayed storage effects are impossible.

Functional evidence: four real isolated-worker/media tests pass, including eight-format decode, orientation/metadata removal, malformed/mismatched/42-megapixel/121-second/input-size rejection, cancellation scratch cleanup, rejection of unsafe runtime configuration, lost derivative begin and expired leases, worker outage/retry, replacement/restore, quota/privacy/revocation and pending-worker purge with late artifacts. `scripts/test-rust-media-sdk.ts` passes through real PostgreSQL, pinned RustFS, actual Rust HTTP, the public vanilla SDK and a genuinely isolated worker. Nonready states render genuine placeholders; retry is explicit only for failed states with `canRetry`. ## Editor r4 host additions

`editors.suggestCopyName({sessionId, parentId, name, intent})` is an authorized query for save-as/export, not replacement. It checks the live editor session, output format and chosen writable destination, then suggests the first unused name among 1,000 bounded candidates in that folder. Suggestions do not reserve names; normal upload publication still handles races. The SDK keeps the selected name with the captured save ID for retries and prohibits changing its extension. Rust owns the operation and generated TypeScript/Query consumers derive from it.

`EditorDocument.annotationAuthor` is optional and contains only a signed-in PDF user's display name. It carries no ID, email, credentials or token. The SDK forwards it only to r4's PDF frame; earlier strict decoders receive the earlier message shape. The PDF adapter uses it for future annotations only; public-link visitors without an account default to Guest and stored annotation authors survive reopening. Real browser save/reopen and saved PDF author bytes were checked for both cases; see [r4 editor evidence and remaining limits](../../docs/artcraft-integration.md#native-host-v3-revision-r4--2026-11-13).
