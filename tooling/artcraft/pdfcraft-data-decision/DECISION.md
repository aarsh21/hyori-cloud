## Why a replacement is not a one-file deletion

Source consumers are retained, not inferred solely from names:

- `crates/fonts/src/std14.rs:95–110` ([2.txt](2.txt)) uses the matrix for character advances and string measurement; lines 118–120 expose the standard base-font name.
- `crates/fonts/src/lib.rs:141–149` ([3.txt](3.txt)) uses the same WinAnsi data when writing characters.
- `crates/fonts/src/pdf.rs:823–838,1207–1208,1257–1265` ([4.txt](4.txt)) uses standard-font widths, glyph-name extraction, named encodings and default StandardEncoding. This affects text extraction/search/redaction as well as generated appearances.
- PDF WinAnsi is **not** an interchangeable Windows-1252 decoder: `0xA0` maps to ordinary space and `0xAD` to ordinary hyphen here; MacRoman `0xCA` also maps to ordinary space. Those exact semantics are checked mechanically.

## Technically viable paths; none implemented

1. **Adopt the supported existing-data evidence if approved.** The follow-up now retains the explicit AFM companion terms, all fourteen complete AFMs, matching numeric results and AGL/PDFium source-specific permissions. Preserve their original notices and conditions in any authorized notice/provenance adoption. This can preserve current format behavior without changing official pins. It is substantive positive evidence, not a restatement of project MIT/Apache; adoption/clearance is not performed by this record.

2. **Derive metrics from the already retained Foxit/PDFium substitute font programs, with a separate encoding-data solution.** Fourteen `vendor/hayro-interpret/assets/Foxit*.pfb` resources have positive byte observations and an asset-specific BSD-3 permission/copyright file ([8.txt](8.txt)). A generator could derive advances from those exact programs and record hashes/transformations rather than copy the existing AFM tables. This is a technical candidate, not an assertion that such a derivation settles every rights question. Crucially, the current `standard_font.rs` ([7.txt](7.txt)) still imports generated AFM-style metrics (`:3,71–84`), and its CFF `advance_width` branch returns `None` (`:329–332`). Calling today's standard-font helper is **not** independent measurement. The follow-up verifies that the already locked raw CFF APIs return widths; the wrapper currently discards that result, so a new production parser is not necessary. Static extraction accounts for all compared slots but measures 16 numeric differences and wider glyph-name coverage gaps, so this is not a drop-in substitute. Character-code and glyph-name-to-Unicode mappings still need their own supported source/derivation; replacing widths alone does not resolve `encodings.rs`.

3. **Use explicit embedded replacement fonts and independently sourced mappings for generated appearances.** A future modified PdfCraft could measure actual selected font programs, embed/subset them and write matching PDF width/Unicode metadata. That avoids pretending substitute metrics are exact Helvetica/Times/Core14 data. It requires approved redistributable font inputs, complete copyright/permission/name handling, a solution for Symbol/Dingbats, and continued handling of existing unembedded standard-font PDFs. No new fonts have been sourced or licensed in this slice. This is a larger behavior/format change requiring a separately approved implementation and acceptance fixtures, not a drop-in change to frozen official WASM.

**Updated recommendation:** accept the follow-up's positive existing-width/AGL permission-and-correspondence basis before requiring a replacement, then decide notice/provenance adoption and the explicit mapping compatibility policy. No width replacement is technically required solely by the former missing-permission concern. Path 2 is measurable but not numerically equivalent; path 3 remains a larger fallback. None is a selected/implemented replacement or deployment/legal approval.

**Not solutions:** copying Hayro's parallel generated metric/encoding tables or the manually typed spot-test values; assuming another project's root SPDX grants all underlying data rights; replacing WinAnsi with a platform codepage; disabling extraction/redaction/appearance capabilities; or claiming absence from a failed byte search.

Any chosen modified build needs its own source/artifact identity, notices, fidelity checks and unchanged separate protected-mark/UI ownership. Required fixtures include all 14 × 256 widths/undefined slots; WinAnsi/MacRoman/Standard and glyph-name/Differences extraction; space/hyphen aliases; Symbol/Dingbats; appearance wrapping/placement; Unicode extraction/search/redaction; PDF save/reopen and rendering consistency. No feature may be silently dropped to avoid the blocker.
